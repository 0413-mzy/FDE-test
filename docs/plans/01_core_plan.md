# 产品主计划：可交互电商业务平台

版本：commerce-direction-v1。日期：2026-10-06。
用户明确要求先建立电商系统，再思考 AI 优化，并随后批准先执行重新定位的第一步。
本文件取代旧“电商订单咨询助手 Core V1”作为产品方向的权威来源。

## 1. 为什么调整

此前围绕咨询取数、Evidence/CaseContext 与未来 AI 回复构建，平台订单来自外部
Sandbox，网页只有基础外壳。这能支持客服辅助实验，却不能让用户和商家共同操作
真实关联的购物、订单、发货和售后流程。

新的目标是先构建可亲自使用、可演示、可复现业务异常的电商平台。再观察重复操作、
沟通成本和处理错误，为 AI 找到具体任务及可比较的收益。

## 2. 产品定义

一个多商家、实体商品的电商业务模拟平台，包含用户端、商家端以及共享业务后端。
模拟的是外部支付与物流，不是订单、库存和双方交互的持久化。

- 用户端：浏览商品、购物车、下单、模拟付款、查看订单与物流、联系商家、确认收货、售后。
- 商家端：商品/SKU与库存管理、订单处理、发货、查看履约状态、消息回复、售后处理。
- 演示操作：受限制的测试入口产生模拟支付结果与物流事件；与真实用户/商家权限区分。
- 共享数据：双方读取同一订单、包裹、会话与售后记录的各自授权视图。

第一版多店铺、实体商品，固定CNY整数分、运费/税费为0；跨店Cart原子下单后拆成各店
独立付款/履约Order。第二步决定见 [领域契约](../commerce/README.md)。
不支持跨境税费、多币种结算或全球物流；没有真实资金、外部短信或实单。

## 3. 核心交互闭环

1. 商家建立商品、SKU、售价与库存，并上架。
2. 用户选商品并提交购买请求，服务器计算价格并检查可售库存。
3. 用户完成模拟付款，结果写入平台；商家在其店铺订单列表看到结果。
4. 商家处理并发货，平台关联订单商品与包裹，用户看到相应履约信息。
5. 演示物流事件推进，双方看到同一个包裹的时间线与更新时间。
6. 用户在对应店铺/订单会话发消息，授权商家可读并回复。
7. 用户确认收货，或提出取消、退款/退货请求，由规则与授权人工操作推进。
8. 关键状态变化和操作结果留痕，刷新或重启后仍可读取。

购买与发货先做通；消息、售后和异常分阶段扩展，不把所有页面同时铺开。
以上是目标流程，不表示当前代码支持这些操作。

## 4. 验收原则

- 双端关联：商家操作后，用户端读取到对应变化；不同账号/店铺不串数据。
- 状态正确：付款、发货、取消、退款等有允许前态及拒绝规则，不能任意改状态。
- 数据可靠：服务器拥有金额与库存事实，重复提交和并发不会重复扣减或超卖。
- 可交互与可恢复：页面真实调用后端，刷新不丢结果，错误能显示并重新查询。
- 场景覆盖可量化：按明确的正常/异常场景矩阵验收，不声称“覆盖绝大多数业务”
  而不给出覆盖边界。场景矩阵在第二步落地。
- 模拟标识：模拟付款/物流始终明确；演示环境不等于可上线经营的平台。

## 5. 复用与清理

保留 FastAPI、React、PostgreSQL、Alembic、密码/会话原语、审计、时钟、测试和 CI。
既有 Agent/Supervisor/Admin 权限属于客服域，不直接映射客户与商家。
保留 Provider 及 Evidence/CaseContext 作为可选模块；不要求商城请求先建立 Inquiry。
商品、库存、交易、包裹、会话和售后将由平台自有领域模型承担。

清理活动文档里的旧产品目标、累积阶段授权和“禁止完整电商平台”的规定。旧契约仍
约束兼容模块；旧验证保留原日期和版本范围。Git 历史保留重设计之前的计划。
不删除数据库、不改写旧迁移、不为换定位删除已验证模块。

## 6. AI 后置

平台人工流程可运行后，收集操作耗时、重复查询、消息量、异常处理成本和错误样本。
候选任务可能是商品信息整理、订单解释、消息草稿或异常摘要；必须先选择具体问题，
建立非 AI 基线与评价标准，再决定实现。当前不实现 AI，也不自动沿旧 Stage 5 推进。
