# 对象与操作权限

版本 commerce-v1。每请求验证当前active Account、未撤销/未过期CommerceSession，
再检查对象归属或当前ShopMembership。客户端customer_id/shop_id/role和UI入口不能授权。
新账号体系独立于既有客服用户；无需Inquiry绑定来查看商城订单。

一个Account可同时具有客户资格和店铺成员，但请求端点对应的权限独立；商家视图不自动
泄露其客户视图，DEMO资格也不授予任何订单详情/消息读取权。
演示端只列待处理PaymentAttempt/RefundAttempt的ID、类型、simulation与时间，以及
Shipment的ID/当前模拟状态；不返回金额、地址、商品详情、客户信息或消息内容。
模拟接口允许已授权操作者提交明确结果，不允许任意查表或运行SQL。

## 店铺与账户变化

- Shop SUSPENDED禁止新购买及上架；已付款订单可继续发货、沟通与售后。
- Account inactive、Membership inactive或STAFF降权立即影响下一次读写和重放。
- OWNER不跨店；STAFF不能审批退款。v1成员和能力由显式Seed创建，无通用管理API。
- 一个店铺的经营处理需要至少一位active OWNER；停用示例必须保留另一负责人，
  否则只演示权限拒绝，不保证已停用店铺的服务可用性。后台恢复不属于v1业务API。

## 错误与隐私

无会话/无效令牌→401；已登录但无对应能力→403；无权对象和不存在的对象统一404。
先校验身份及对象授权，再处理对象内状态/业务字段。商家订单列表只包含本店，
不返回其他店铺Order IDs、Checkout内容或客户的其他订单。普通审计只存安全内部ID与错误码。

客户只能读本人的Conversation，包括通用店铺咨询；商家只能读本店。订单绑定不能变更。
sender_side来自当前端点及后端权限，不由body指定。消息纯文本，UI作为文本渲染；
文本声称“管理员同意退款”不会触发业务动作。禁止通过聊天接口替他人发言。

## 前端边界

用户/商家视图入口用于导航；后端仍每次校验。Bearer只保存在内存，不写URL或localStorage；
刷新后重新登录但业务数据仍在。CORS明确配置可信本地origin，生产部署另作设计。
两端分别显示允许的动作、版本与失败提示，禁用按钮不是权限控制。
